## Concrete gaps addressed in this scope

The reviewed build instructions manually copied static/public directories into build output, had no immutable paired release manifest or byte-integrity check, and did not specify backups/restores or a rollback decision. A process launch and a single `/service` URL were the readiness guidance. The installed release paths were source-independent in the recorded runbook, but Node/runtime dependencies and the API/frontend provenance boundary were implicit.

Added `scripts/deployment/research_delivery.py`, a stdlib-only Python 3.9+ command with five operations:

- `package` copies already-built API, standalone dependencies and separate static/public inputs to a new directory. Static/public assets replace stale staged copies; build inputs and prior releases are untouched. Both source SHAs are supplied explicitly. A manifest stores actual entry hashes, sizes, executable flags, relative links, empty directories, Next build ID, target and declared Node version. Copied inventories must match input inventories. Environment/common package credential files and external/absolute/dangling links are rejected; other secrets still require input review.
- `verify` checks the entire inventory, not just selected artifacts, including missing/extra entries and executable-bit changes. It validates the frontend build ID or the backup's offline attestation. Manifests are unsigned, trusted local evidence, not adversarial authenticity guarantees.
- `ready` verifies the release, compares direct/proxied service schema, identity and capabilities, requires HTML at `/experiments`, and checks one packaged static JavaScript file's exact bytes. It uses bounded GETs, normal HTTPS validation, no HTTP redirects or environment proxy, and permits plain HTTP only on loopback. It does not assert full frontend build identity from one shared asset or API commit identity from a fixed service string. Supervisor paths and release evidence remain necessary.
- `backup` requires `--writers-stopped`, explicitly declaring every writer and automatic restart disabled until completion. It copies the **whole** API data root including idempotency records, native artifacts, diagnostics and unknown files, then checks full before/after/copied inventories. It refuses symlinks and special files. Metadata states `operator-declared-writers-stopped`; observed unchanged bytes do not prove quiescence. The script cannot stop or identify all possible writers, and must not be used as a live backup tool.
- `restore` verifies a backup and copies/checks it into a new data directory. It never overwrites data, parses/repairs records, starts an API, or changes supervisors. Application restore validation is a separate planned drill using another disposable copy.

All writes use new sibling staging directories and same-filesystem rename on success. A destination lock prevents simultaneous tool writers using that name. Existing targets, source/output overlap, unreadable inventory directories, copy failures and observed mutations fail closed. Staging is removed on ordinary exceptions; abrupt termination may leave an operation's private staging/lock directory. Trusted operators must keep inputs/outputs stable; the lock is not honored by the API and the code is not designed for hostile concurrent filesystem writers. No power-loss guarantees are claimed.

DEPLOYMENT now describes paired release provenance, same-target Node/native requirements, loopback/private readiness, absolute supervisor paths, offline backup prerequisites, exact-byte versus application restore checks, plist bootstrap after argument changes, binary versus data rollback, log handling and the outstanding CI gaps. Runtime configurations remain host-specific and uncommitted. No framework or configuration abstraction was introduced.
